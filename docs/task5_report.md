## Problem

The backend could already tell an operator that a fridge was above 8 °C. That answer arrives after the vaccine inside has started spending its heat budget, which is the wrong moment to learn anything. Task 5 reads the same stored rows three more ways: a forecast of the next 30 minutes, a 0-100 compressor health score that is meant to drift before the temperature does, and a relocation plan that turns the two into one move an operator can confirm. Every number is served by a route and printed with the figures it came from - there is no score the page can show but the backend cannot explain.

## Dataset

12 streams over 6 scenarios (compressor_failure, door_left_open, heavy_loading, normal, power_failure, weak_compressor) = 120,432 one-minute windows, from `ml/generate_data.py --seed 7`. Each stream is a fridge with a duty cycle, a room temperature, a compressor that cools in steps and faults injected at fixed minutes. Split oldest-to-newest inside each stream: 83,940 train, 17,700 validation and 18,072 test windows, with a 30-minute purge around the 2 time walls (720 rows dropped) so a feature that looks backwards cannot reach into the window it is being scored on.

## Features

16 numbers per window, computed by `backend/app/ai/features.py` - the same file the running server imports, so a feature cannot be built one way at training and another way in service: `temp_last`, `mean_5`, `mean_15`, `slope_5`, `slope_15`, `max_15`, `min_15`, `above8_min`, `duty_15`, `door_min_15`, `power_off_min_15`, `dev_from_mean`, `flags_known`, `hour_sin`, `hour_cos`, `history_min`. They need 15 contiguous minutes before any of them exists, which is why a fridge that has just been plugged in is refused instead of guessed at. The compressor-derived features (`duty_15`, `door_min_15`, `power_off_min_15`) are the same signals the health score reads, and `flags_known` tells the model when a node does not report those pins at all.

### Temperature on the held-out windows

### Compressor health

backend/app/ai/compressor.py score(), re-run on the rows up to each cut, one cut every 360 minutes from minute 1440 of the stream. It is not a fitted model: it has no held-out wear and no accuracy to quote. What is measured is direction and collateral damage.

| check | expected | measured |
|---|---|---|
| the score falls on a weakening compressor | start minus end at least 10 points | 97.0 then 32.0, a fall of 65.0 points |
| a healthy compressor is not called weak | at most 5% of rolling points in the weak band | 0 of 48 points = 0.0% |

On the stream whose pull is deliberately decayed, the score runs 97.0 → 32.0 with 20 of 48 points below 50; on the streams given no fault it never enters that band (0 of 48 points). The page shows the number with its reason lines, so an operator can disagree with it.

## How relocation decides

`GET /api/ai/relocations` forecasts every fridge (with `episode=False`, so two operators refreshing the page cannot spend the one breach warning a heat wave is allowed to raise) and then applies plain rules. A fridge is at risk when it is reporting over 8 °C now or its forecast peak crosses that line. A destination must be online within 20 s, on mains, door shut, forecast risk not high, health score at least 50 and one place free, where a fridge is assumed to hold 6 batches unless `MAX_BATCHES_PER_FRIDGE` says otherwise. Batches are offered in order of remaining budget minutes, destinations ranked by temperature then health, and a free place is spent as it is promised, so two batches are never told the same slot is theirs. A suggestion id hashes batch, source, destination and the current 10-minute window, so the page cannot confirm a stale plan.

`POST /api/ai/relocations/confirm` - pharmacist or admin only - recomputes the plan on the server, answers 409 with the reason the move is no longer there if it is not, and otherwise performs it through the same batch-move code the Inventory page already uses, writes a `RELOCATION_CONFIRMED` row into the audit chain; a second click on the same suggestion is answered from that row rather than by moving the batch again. The temperature, budget minutes, free places and blockers on the card are the ones the decision used.

The `watch` band begins 0.5 °C below the threshold, which is about one model error: the peak head measures 0.3351 °C MAE on the test windows. A fridge predicted to stop within one error of the line is worth a look rather than reported as safe. Separately, a heat episode must fall 0.4 °C under the line before a new episode is counted, so one long warm afternoon arrives as one warning rather than as five.

## Limitations

- the streams scored here come from the same generator, physics and seed as the ones the model was fitted on; they are separated by a wall in time plus a purge, not by a different process
- no row in this file came from a real fridge, so no number here is a real-fridge accuracy
- metrics are computed from the standard-library walk in backend/app/ai/predict.py, which is the code the deployed backend runs, not from sklearn
- normal and weak_compressor never cross the line in the generator, so for those streams the only thing measured is how often the model cries wolf
- a minute-window is one sample, so the precision and recall above weigh a long breach many times; the episode table weighs each breach once
- the exported walk and sklearn do not agree bit for bit - sklearn walks its trees on a float32 copy of the features, so a few windows per head take the other branch at a split. stdlib_walk_check prints the gap and the run fails if it grows
- compressor_health is a rule, not a fitted model: it has no held-out set and no accuracy to quote. What is measured is direction (does it fall on the stream where the pull decays) and the false-alarm rate on the streams that were never given a fault
- the health score's baseline is a fridge's own earliest cycles, so it measures drift away from the start of stored history: a compressor installed already worn, or one whose history was wiped, is graded against its own bad behaviour and reads healthy. Nothing in this data can show that limitation, because every stream starts at full pull

- a node that reports less often than every 20 s reads as offline, so it can never be a destination: on a fleet that phones home once a minute the plan says "nowhere to go" correctly and permanently. That threshold is a site decision, and it is the first thing to check when the panel looks empty.
- 6 batches per fridge is declared, not measured. Nothing in the database knows the size of a fridge, so the capacity the rules protect is one number a person has to get right.
- the forecast has never met a real door seal, defrost cycle or ward power cut. These numbers describe the pipeline, and the pipeline is the only thing being claimed.
- relocation is deterministic: same readings, same suggestion. It cannot learn that a particular ward always recovers on its own, and it should not try to before somebody has watched it.
